Orchestration / control flow

The files that decide what happens next — routing a request, running the model's tool-use loop, and firing unattended work on a schedule.

FileWhat it does
app.pyThe FastAPI route layer — every HTTP endpoint in the system. Wires requests to the agent, tools, and database; runs startup steps (applying migrations, launching the scheduled-task poller); wraps route logic in broad exception handling to return clean JSON errors instead of raw stack traces.
hermes/agent.pyThe actual agent loop — run_turn / stream_turn. Builds the system prompt, calls Claude (or OpenAI as an alternate provider), and dispatches whatever tool calls the model makes. Bounded by Config.MAX_TOOL_ITERATIONS — a fixed for loop, not open-ended recursion.
hermes/tools.pybuild_tools() assembles the tool list, gated by which apps are actually connected for the current business. dispatch() routes a model's tool-call to its handler. This is the real control-flow hinge between "the model decided to act" and "something actually happened."
hermes/scheduler.pyTurns a saved Scheduled Task into a bounded, unattended agent run — schedule math (daily/weekly/hourly), restricting the toolset to the task's allowed apps, and prepending the autonomy guardrail text.
hermes/job_runner.pyThe sibling orchestrator for code-driven Jobs (not agent-prompt-driven) — a plain Python function registry (REGISTRY) that mirrors the scheduler's timing logic but fires a registered function instead of a prompt.

State handling

Two distinct layers: fast in-process memory for the live conversation, and Postgres for anything that needs to survive a restart.

FileWhat it does
hermes/memory.pyIn-process, thread-safe conversation store keyed by session_id — the Claude message list (the model's actual working memory) plus a lightweight display transcript for the UI's history sidebar. Explicitly documented as swappable for Redis/a database; on its own it does not survive a process restart.
hermes/db/connection.pyThe real durability layer — Postgres on AWS RDS. Two auth modes: a static password, or a short-lived (~15 min) IAM token generated fresh per connection via boto3. SSL is mandatory. This is where everything that needs to persist actually lands.
hermes/db/bills.py, conversations.py, meetings.py, scheduled_tasks.py, jobs.py, documents.py, memories.pyOne module per persisted concern — the read/write layer for each table (bills, chat history, meeting sessions, scheduled tasks, jobs, knowledge-base documents, extracted memories).
hermes/memory_extract.py / hermes/memory_retrieve.pyCross-turn persistent memory — silently extracts durable owner/business facts after each turn (background thread, no added latency), and recalls relevant ones semantically before future turns.
hermes/attachments.pyMulti-tenant attachment store scoped by entity_id — upload once, reference by id across chat turns.

Tool / retrieval use

How the assistant reaches external systems, and how it searches its own knowledge base.

FileWhat it does
hermes/tools.pyTool definitions and dispatch — dedicated tools (send_email, calendar_list_upcoming, etc.) plus the universal maton_request, which can hit any endpoint of any connected app.
hermes/maton.pyThe actual outbound gateway client — proxies calls to Gmail, Calendar, QuickBooks, and every other connected app through Maton's OAuth-holding API.
hermes/search.py + hermes/vector_store.pyRetrieval for the main app — pgvector-backed semantic search over the knowledge base, scoped by business and a sensitivity ceiling (public < internal < confidential < restricted).
hermes/ingest.pyThe chunk → embed → upsert pipeline that populates that pgvector store from uploaded documents.
ingestion-service/ingestion/pinecone_store.pyA separate, still-Pinecone-backed retrieval index used by the standalone background ingestion service. This is a real architectural split, not just a documentation caveat — see the callout below.
hermes/wati.py, hermes/fathom.py, hermes/worldbank.py, hermes/voice.pyNarrower tool-adjacent integrations — WhatsApp Business, meeting notes/recordings, public macro data, and speech-to-text/text-to-speech.

Split-brain retrieval: the main app reads from pgvector, but the standalone ingestion service still writes to Pinecone. Anything that service indexes today does not land where the main assistant's search actually looks — confirmed directly in the code, not just in the docs.

Guardrails / failure handling

Safety in this system is real but largely enforced by instructing the model, not by hard code paths that physically prevent an action. Worth being precise about which is which.

FileWhat it doesEnforcement
hermes/agent.pyThe system prompt directly instructs the model: for any write or destructive action, state exactly what it will do and stop to wait for confirmation.Prompt-level
hermes/tools.pyFile-send tools use a two-step confirm/draft_id pattern — prepare without confirm, only actually send with confirm=true plus the returned id. _TOOL_REQUIRED_APPS removes a tool from the list entirely if its app isn't connected.Code-level
hermes/scheduler.pyVALID_AUTONOMY = {"readonly","draft","full"} with guardrail text prepended per unattended run.Prompt-level (the toolset restriction to a task's allowed apps is the code-level part)
app.pyDozens of deliberately broad except Exception blocks that convert internal failures into clean JSON error responses instead of raw stack traces; several explicitly wrap startup steps (migrations, the poller) so one failing doesn't block the whole app from booting.Code-level
hermes/db/connection.pyCredential guardrail — IAM auth tokens expire in ~15 minutes and are regenerated per connection rather than cached; SSL is mandatory.Code-level

Tests / evals

Four files total, committed to the repository. One of them is a genuine model-behavior eval, not just a unit test.

FileWhat it actually checks
tests/test_api.pyOffline end-to-end API tests. Network-bound calls (Claude's run_turn, voice transcribe/synthesize) are monkeypatched, so it runs without real API keys or connectivity.
tests/test_scheduled_window.pyPure unit tests for the scheduled-task date-window/backfill math — advance_window, build_run_prompt, initial_next_run. No database or agent required.
tests/test_worldbank_tool_triggering.py + tests/worldbank_tool_questions.jsonAn actual eval harness — replays the agent's first tool-selection decision against real questions to check whether the worldbank_data tool fires when it should, and doesn't when it shouldn't. This is the one genuine model-behavior eval in the repository.

Not in the bundle: tests/test_bills.py exists in the working directory right now but was never committed — it is not part of the git bundle's history at all.

Logging

This is the one category where the honest answer is close to "doesn't really exist" as a system — worth saying directly rather than softening it.

Python's standard-library logging module is used directly — the pattern import logging / log = logging.getLogger("hermes.scheduler") appears across roughly 18 files in hermes/ and in app.py. But:

There is no logging.basicConfig call anywhere in the codebase — confirmed by searching the entire repository, not inferred. No central logging configuration, no structured/JSON logging, and no log aggregation or APM/observability service (no Sentry, Datadog, or OpenTelemetry, in the code or in requirements.txt).

Practically, this means that without the deployment environment configuring logging separately, most log.info(...) calls default to Python's built-in behavior — WARNING level and above only, printed unformatted to stderr. Routine info-level logging throughout the app is effectively silent in most deployments. This is a real, current gap in the code as it stands, not a stylistic choice.
